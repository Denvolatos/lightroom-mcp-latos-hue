## 实验 2：插件用 LrHttp 访问本机 Python 服务（2026-11-01，Lightroom Classic 15.2.0）

**做法**：`server/exp2_server.py`（标准库，只绑 `127.0.0.1:58770`，随机口令 + Host/Origin 检查）；插件菜单 `LrMCP: HTTP test (experiment 2)` 发 GET 请求。

| 测试 | 结果 |
|---|---|
| T1 口令正确 | ✅ 200，5 ms |
| T2 口令错误 | ✅ 401 |
| T3 带 Origin 头（模拟网页乱连） | ✅ 403 |
| T4 连续 10 次请求延迟 | ✅ 平均 1.5 ms，最差 8.5 ms |
| T5 服务端慢 3 秒、超时 10 秒 | ✅ 200，耗时 3003 ms（长轮询可行） |
| T6 服务端慢 5 秒、超时 2 秒 | ✅ `timedOut`，**实际约 4 秒才返回**（超时是「每个阶段」各算一次，实际约为设定值的 2 倍） |

**结论**：方案 B1（Python 本机 HTTP 服务 + 插件 LrHttp 请求）**在 Windows + LrC 15.2 上可行**，没有被系统代理干扰，延迟极低。

**LrHttp 实际发送的请求头**：`Accept`、`Authorization`、`Content-Type: text/plain`（除非自己指定）、`User-Agent: Adobe Photoshop Lightroom`、`Host`、`Cache-Control`；**不带 Origin**（我们测试时手动加的）。

**重要发现：Claude 桌面版的文件重定向（MSIX）**
- Claude 桌面版是商店（MSIX）应用，从它启动的程序（包括 Claude Code 的 shell、由它启动的 MCP 服务）往 `AppData\Local` 写的文件，会被重定向到 `AppData\Local\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Local\...`。
- 在它里面看得到文件，Lightroom 等外部程序看不到（`LrFileUtils.exists` = false）。
- **规则：插件与服务之间共享的文件（口令、端口）不能放在 AppData；用 `C:\Users\<用户>\LrMcp\`**（用户目录下，不在 AppData 内，实测可见）。HTTP 通信走网络，不受影响。
- Lightroom 里读文件：`io.open` 对非 AppData 路径可用；SDK 文档推荐 `LrFileUtils.readFile`/`exists`。`os.getenv` 不可用，用户目录用 `LrPathUtils.getStandardFilePath("home")`。

**待办/注意**：
- 只测了 GET；POST + JSON 正文待测（需显式指定 `Content-Type: application/json`）。
- 服务端要处理客户端超时断开（`BrokenPipe`），实验里被超时中断的请求没有写日志。
- 令牌文件的 ACL（仅当前用户可读）还没做。
- Origin 校验只是手动模拟，LrHttp 自己不带 Origin，浏览器带，所以规则成立。

**下一步**：实验 3（LrSocket 双端口，作对照）、实验 4（读写参数、导出 JPEG、快照还原）。

## 实验 3：LrSocket 双端口（2026-11-01，Lightroom Classic 15.2.0）

**做法**：插件菜单 `LrMCP: Socket test (experiment 3)` 开两个 LrSocket（一个 `receive`、一个 `send`，`address="localhost"`、`port=0`），端口写入 `~/LrMcp/sock_ports`；`server/exp3_client.py` 读端口后连接并测试。

| 测试 | 结果 |
|---|---|
| 监听地址（`netstat -ano`） | ✅ **仅 `127.0.0.1`**，端口 1624/1625（系统分配），属于 Lightroom 进程；未见 `0.0.0.0` 或 IPv6 监听 |
| 认证 | ✅ 未认证发命令 → `denied`；错口令 → `auth fail`；对口令 → `auth ok` |
| 20 次往返 | ✅ 平均 3.4 ms，最慢 4.0 ms，0 错误 |
| 64 KB 单条消息 | ✅ 完整（65540 字节），未被切断 |
| 结束 | ✅ 插件关闭后客户端读到干净的断开 |
| 不带换行的消息 | ⚠️ `ping 99`（无换行）插件**完全没收到**；之后补发换行，插件收到的是一条**长度 0 的空消息**。结论：**每条消息必须以换行结尾，一行一条**；LrSocket 交给 `onMessage` 的内容已去掉结尾换行 |

**其他观察**：
- 客户端要先连 `receive` 口（我们往里写）和 `send` 口（我们从里读），各一个连接。
- 官方样例与社区都提到：`receive` 口长时间没客户端会触发 `onError("timeout")`，插件里要 `reconnect()`；本次客户端立即连上，**未触发，待单独测**。
- 端口随机且很小（1624），要靠文件交接端口。
- 每个 socket 一次只接一个客户端 → 多个 MCP 服务进程同时连会冲突。

**结论**：B2 在 Windows + LrC 15.2 上也可行（仅本机、可认证、低延迟）。**首选仍是 B1**（端口固定、插件重载不换端口、Python 重启可自愈）；B2 作已验证备选。

**设计问题（待决）**：同时开多个 Claude/Codex 会话时，每个会话可能各启一个 MCP 服务进程，会抢同一个端口。v1.0 建议只支持一个，后来的进程给出清晰的中文提示；多会话共享以后再做。

**下一步**：实验 4（读写参数、导出 JPEG、快照还原）。

## 实验 4：读写参数、导出预览、快照与撤销（2026-11-01，Lightroom Classic 15.2.0，Windows）

**做法**：`Develop.lua`（第一、二轮）、`Restore.lua`（4b）、`Wb.lua`（4c）、`Probe.lua`（4d）、`Prepare.lua`/`devscripts/exp4e.lua`（4e）。只改 `ceshi` 测试目录里的照片，改后都还原。

| 项目 | 结果 |
|---|---|
| 读全部参数 `photo:getDevelopSettings()` | ✅ RAW 约 175 个键、JPEG 约 171 个键，耗时 5～19 ms |
| **写参数必须放进 `catalog:withWriteAccessDo`** | ⚠️ 官方文档没写，**实测不放会报错**：`must be called from within a withWriteAccessDo block` |
| 写入后读回 | ✅ 曝光 +0.3、自然饱和度 +10 读回完全一致 |
| 改**没选中**的照片 | ✅ 可以（0 → 0.1 再还原），**不需要选中，也不需要 Develop 模块** |
| 用保存的原值还原 | ✅ **精确还原**，是唯一可靠的还原方式 |
| 1024 px JPEG 预览导出（`LrExportSession`，q=0.8，sRGB，写到 `~/LrMcp`） | ✅ 首次约 1 s、之后约 0.5 s，约 290 KB；改前改后文件不同；Claude 能直接读到图片 |
| `photo:createDevelopSnapshot` | ✅ 能建，`getDevelopSnapshots` 返回 `snapshotID`、`name`、`id_global` |
| `photo:applyDevelopSnapshot(id)` | ❌ 返回成功但**什么都没变**（`snapshotID`、`id_global` 都试过，放进写入门也一样） |
| `photo:deleteDevelopSnapshot(id)` | ❌ 同样静默无效 → **设计里不用快照**（测试照片上残留 1 个 `LrMCP-exp4` 快照，无害） |
| `LrUndo.undo()` | ⚠️ **不稳定**：第一轮一步撤销了两处改动；第二轮连续写入后撤销没生效 → 不作为还原手段 |
| 自定义白平衡写入 | ✅ `WhiteBalance="Custom"` + `Temperature` + `Tint` 可写并读回 |
| **只写 `WhiteBalance="As Shot"`** | ⚠️ 只改标签，**画面不恢复**（预览 298937 B ≠ 原 286204 B，Temperature 仍是旧值） |
| 显式写 `As Shot` + 原 Temperature/Tint（5550/13） | ✅ 预览大小回到 286204 B，与原图一致 → **还原白平衡必须连数值一起写回** |
| Temperature/Tint 何时出现 | 没动过的 RAW 读不到这两个键；写入过后会**稍后**出现（4d 立刻读仍为空，几分钟后 4e 都有了：5450～5600 K，Tint 13）；**JPEG 一直没有**。等待多久：待验证（现有 RAW 都已被动过） |
| 小改再还原（曝光 +0.01 再回原值） | ✅ **0 个键有差异**，预览文件大小完全一致 |
| 官方键表缺 `Temperature`/`Tint`/ `Texture`？ | `Texture` 存在；`Temperature`/`Tint` 如上；`ProcessVersion` 实测为 `15.4`；`Look` 是个表 |

**设计结论**：
1. 一切写入都放进 `withWriteAccessDo`，每次修改用命名历史步骤（`applyDevelopSettings(settings, 历史名)`）。
2. 还原 = 改前读全部相关原值（含 Temperature/Tint）存盘，需要时写回；**不依赖快照和撤销**。
3. 改 RAW 白平衡前：若读不到 Temperature/Tint，先做一次值不变的写入并**轮询等待**其出现（待验证时长），拿到后再改；还原时显式写回。
4. JPEG 的白平衡改动语义不同（没有开尔文值），第一版先不做 JPEG 的白平衡写入，或另测。
5. 预览：1024 px、q=0.8、sRGB，约 0.5～1 s、约 300 KB，一张图 ≈ 1.3k token（估计）。

## 开发通道（2026-11-01 晚）

为避免每次实验都要用户手点菜单，做了**仅限开发**的通道：`server/dev_bridge.py`（127.0.0.1:58770，口令，Host/Origin 检查）、`server/dev_run.py`（命令行运行器）、插件 `DevLoop.lua`（Init 时启动，轮询）。

- 只传**脚本名字**（纯文件名），插件只运行自己文件夹里 `devscripts/` 下的脚本；必须存在开关文件 `~/LrMcp/dev_enabled`（服务启动时创建、停止时删除）；脚本自己还检查目录路径含 `ceshi`。发布版不包含 `DevLoop.lua` 和 `devscripts/`。
- 先尝试读 `~/LrMcp/scripts` 的任意路径版本被系统安全检查拦下，改成了上面更窄的版本。
- ✅ 实测：重新载入插件两次，旧循环被新循环叫停（代际机制有效）；`hello.lua` 与 `exp4e.lua` 全程无需用户操作。

## 实验 5：滑块取值范围与越界行为（2026-11-02，Lightroom Classic 15.2.0，Windows）

**做法**：开发脚本 `devscripts/probe_ranges.lua`，在测试目录的选中照片上，对 14 个有代表性的滑块（曝光、对比度、高光、阴影、白色、黑色、纹理、清晰度、去朦胧、自然饱和度、饱和度、HSL 的红色三项）依次写入「名义最小值、最小值再小 1、名义最大值、最大值再大 1、小数 0.123456」，读回 Lightroom 实际存下的值，最后写回原值并逐项比较。

| 项目 | 结果 |
|---|---|
| 名义最小/最大值（曝光 ±5，其余 ±100） | ✅ 都能写入并原样读回 |
| **越界值（曝光 ±6，其余 ±101）** | ⚠️ **`applyDevelopSettings` 不截断、不报错，原样存下** —— Lightroom 不会替我们检查范围 |
| 小数 `0.123456` | ✅ 原样保存，没有舍入 |
| 全部写回原值后 | ✅ 0 个简单参数与开始时不同 |

**结论**：
1. **范围检查必须由我们自己做**（服务端和插件各做一遍，已经这样做）；不能指望 Lightroom 拒绝越界。
2. 我们采用的范围（曝光 ±5，其余 ±100）是 Lightroom 界面里的常规范围，**并不是通过 API 测出来的**（API 对越界照单全收，测不出真实上限）。把它们当作「保守且符合界面」的限制，而不是 Adobe 官方保证的范围。
3. 写入后不需要担心小数被舍入，`verified`（读回核对）用 1e-3 的容差已足够。
